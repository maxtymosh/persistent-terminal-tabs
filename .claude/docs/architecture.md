# Persistent Terminal Tabs — architecture decisions

> Updated: Nov 6, 2026

## Initial view location — 1.5.1

- `[DECISION]` New installs use the native `vscode.moveViews` command to put `terminalTabs.tree` in `workbench.panel.terminal`, sharing the Terminal container horizontally rather than creating a separate panel tab. This command was checked in installed VS Code and upstream 1.85.2 source. The view and original contribution IDs stay stable to preserve upgrades and existing saved locations.
- Apply once per local profile using the `terminalTabs.defaultViewLocation.v1` Memento marker. Legacy global `state.json` or any workspace-slice directory identifies an existing installation; snapshot this before activation writes state. Upgrades are marked initialized without moving anything. With no Memento, stay passive. Mark before moving, so failed/unsupported commands and later user moves never cause repeated startup layout changes. An explicit Dock Beside Terminal command provides recovery/repositioning.
- The shortcut targets `terminalTabs.tree.focus`, following the view wherever VS Code stores it. No VS Code settings or storage database is rewritten. Manual resets still use VS Code's declared original container; the docking command restores the preferred arrangement.
- Validation: 55 tests pass, including fresh/legacy/second activation, failure/unsupported-command paths, migration evidence and shortcut/command wiring. Native Dock Beside Terminal completed inside an isolated Extension Development Host; renderer log confirms PTT_NATIVE_DOCK_SUCCEEDED. VS Code extension tests use in-memory view storage, so that native smoke does not claim persistence across full app restarts; marker behavior is covered by automated tests.

## Group terminal layout — 1.5.0

- `[DECISION]` `Group.layout` persists `split` or `separate`; omitted legacy values retain split behavior. Group clicks, new chats, reopen and all render paths use this preference through the shared split-anchor resolver. Explicit Combine returns to split mode only after any large-group confirmation succeeds.
- Uncombine uses VS Code's native `workbench.action.terminal.unsplit` sequentially on the group's currently open terminals. It never disposes/recreates shells or opens sleeping chats. Move siblings in panel order, then visit the first pane last, because native Unsplit appends terminal groups. Restore the previously active chat within the group. Group membership and session metadata remain intact.
- Both Combine and Uncombine remain available as row buttons, context actions and palette commands. The preference records PTT's intended layout; manual native-tab arrangement is not observable through the public terminal API.
- Native command semantics were inspected in the installed VS Code workbench: Unsplit removes an instance from its group and creates a new group around that same instance. Automated registered-command tests model that operation and verify lossless separation and ordering; live UI acceptance is recorded separately.

## Group projects

- `[DECISION]` The existing panel remains the single arrangement source of truth. Clicking a group still opens its native split tab. Add Group and the dedicated Choose Project Folder action use a native VS Code QuickPick.
- `[DECISION]` `Group.cwd` is the explicit new-chat default and `Group.projectName` stores the chosen project's display name. Empty groups retain both. Explicitly assigned groups do not auto-rename from their chats. Legacy groups still infer a dominant cwd (newest wins ties); the unbound inbox defaults to home.
- Existing `SessionMeta.cwd` remains authoritative for conversation recovery. Changing a group's project or moving a chat does not rewrite existing session metadata or issue cd to a running process.
- New-chat commands validate an explicit group folder before adding state or creating a terminal. Missing folders require repair; no silent fallback to home. `TerminalOptions.cwd` and tmux's `new-session -c` receive the resolved session folder.
- Named recent projects are stored locally in `~/.terminal-tabs/projects.json`, separately from workspace slices. Default names use the final folder component; picker pencil edits aliases. Read-before-write plus atomic replace preserve sequential choices across windows. At most 100 recent folders are retained.
- Directory discovery uses asynchronous filesystem directory listings of local workspace roots and `terminalTabs.projectSearchRoots`. It reads no file contents, skips hidden/generated directories and symlink directories, and stops at eight levels and 8,000 directories per root. Each root has a separate budget so large runtime trees cannot starve document roots.
- Search ranks exact/prefix/substring/fuzzy project-name matches before path-only matches, with recent and short names prioritized within matching tiers. Only 200 suggestions render; Browse and typed absolute paths remain available. Discovery repaints are throttled and canceled when the picker closes.

[Repository tasks](../tasks/tasks.md) retain their established legacy format. New concrete work uses individual task records alongside the existing index. No v3 migration or GitHub issue sync is configured for this repository; historical tasks remain intact.

## Shared agent status — 1.4.0

- `[DECISION]` One application-independent engine returns working/waiting/idle/unknown with an evidence source. Models are not detector identities. Native adapters and the generic bridge feed the same polling/cache/tree path. Blue is working; filled grey is unknown and bell is waiting. Known idle/waiting keep green/yellow attachment colors; unknown attachment remains in the tooltip. Supersedes the 1.4.0 question icon and blanket plain-title unknown decision: native Codex thread/project idle titles must clear unknown. Empty/unrecognized formats remain unknown. Codex title detection assumes default animated activity or explicit run-state; customized titles that remove state cannot provide reliable work evidence. Both approval blink phases are recognized.
- `[INTEGRATION]` Gemini CLI 0.56.0 registers its actual Node process through a passive SessionStart hook; native dynamic title provides Ready, Working (including silent work) and Action Required. Real isolated tmux idle/work/cancellation/idle passed against a local fake provider. No inference or screen heuristic was used. Its AfterAgent hook is not authoritative because abort paths can skip it.
- `[INTEGRATION]` The shared reporter binds schema, PID, UTC process birth, session, pane ancestry and foreground TTY/group. It writes bounded records atomically under a per-process nonce lock, rejects older event updates and preserves long quiet work without an expiry. Generic local-client working/waiting/idle/unknown/exit passed a real tmux fixture; `scripts/check-live-status.py` reproduces it.
- `[DECISION]` Grok remains explicitly unknown. Source hooks and PID binding were implemented and tested, but real Grok 1.0.70 cancellation left both hooks and native turn status stale after the UI returned to its prompt. A temporary native status-line observer confirmed the same failure. The engine gates Grok rather than reintroducing known false blue; the test hook installed during research was removed with a local backup. No Grok status-line configuration ships.
- The explicit `status-setup` command installs a stable, atomically switched generic reporter plus the named Gemini registration while preserving unrelated JSON settings and local backups. Gemini hooks load on normal agent restart; no user chat is killed. JSONC is refused rather than flattened. ACP is an integration source only when a client owns the connection; no universal passive interception is claimed.
- Public integration contract and limits: [agent-status.md](../../docs/agent-status.md). Unsupported applications and model servers remain unknown until an application reports its own lifecycle.

## Prior working-dot implementation — 1.3.3 (native Claude/Codex substrate)



- `[DECISION]` Native Codex OSC busy title plus verified live process ownership determines blue. tmux's `pane_current_command` is diagnostic only for work detection: noninteractive zsh launch wrappers share a foreground process group with Codex, and tmux may select zsh. Do not regress to exact foreground-command equality, screen changes, activity timestamps, busy-text searches, or a linger timer.
- One shared `ps` snapshot provides pid/parent, process group, terminal foreground group, TTY, process state, RSS and executable (`comm`, never argv). Resolve descendants of the pane root on that same TTY and foreground group, rejecting stopped/zombie processes. Stop traversal at an owning agent so nested tools cannot supply another UI's identity. Reuse this snapshot for the existing RAM totals.
- Missing process evidence clears blue; it never enables a title-only or cached-blue fallback. Attachment still uses tmux's attachment count. Completion, approval and exit clear on the next configured poll (default eight seconds). No screen capture is needed, including narrow/detached panes.
- `[INTEGRATION]` Claude now uses its native `~/.claude/sessions/<foreground-pid>.json` registry (or `CLAUDE_CONFIG_DIR`), the same state exposed by `claude agents --json`. Read only exact `.json` records, never adjacent `.key` files. Verify PID, normalized UTC/C-locale `ps lstart` against `procStart`, `kind: interactive`, session identity presence and tmux session name. Accept only `busy`, `idle`, `waiting`; only busy is blue. Versioned native executable names resolve as Claude candidates, but the verified record is still required.
- Native Claude busy includes delegated work while its main prompt is idle; waiting includes permission/input dialogs. Registry timestamps mark transitions, not heartbeats, so quiet or long work has no arbitrary expiry. Missing/partial/oversized records, process exit, changed process birth or unknown schemas clear blue on the next poll. No global hooks or transcript parsing are installed. The existing session tracker last_event cannot establish work: Stop can coexist with active delegated tasks and does not cover user interruption.
- Claude's `✳` title remains static in idle and busy states. The screenshot failure was missing Claude coverage in 1.3.2, not a Codex wrapper regression. Claude 2.1.314 and 2.1.316 native implementations and live states were inspected; older versions lacking the native registry, Grok and Antigravity remain attachment-only.
- `[DECISION]` On extension-host restart, adopt existing VS Code terminals only when their processId exactly matches a live PTT tmux client belonging uniquely to this workspace. Lazy startup retains these terminals and their split layout; no detached/cold session is launched. Unverified stray cleanup retains its previous behavior. This is extension-host restart support, not preservation of transient terminals through a full window reload. The small-workspace open-on-startup path still disposes/rebuilds the saved set.
- Diagnose Dots records raw command, verified agent and presence of the busy-title marker without recording conversation titles. Activation records the extension version so future investigations can distinguish loaded from merely compiled/installed code.
- Regression evidence: actual screenshot session had pane root zsh PID 4262 and live Codex child PID 4302, both foreground group 4262 on ttys010. Old detector returned false; repaired detector true. An isolated real tmux server reproduced the wrapper and passed idle → work → approval → completion → work → exit with a deliberately retained spinner. User sessions were not manipulated by that test.
